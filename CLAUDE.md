# CLAUDE.md — CAR·COPILOT project

## What this is

CAR·COPILOT is a Gemma-4-powered on-device car diagnostic assistant for the Kaggle Gemma 4 for Good hackathon. The complete technical specification is in `carcopilot_design.md` in this directory. **Read that file before doing anything else.** The interactive UI mockup is in `carcopilot_mockup_v09.html` — open or inspect it whenever you need to understand what a screen should render.

## Source of truth

- `carcopilot_design.md` is the spec. When in doubt, defer to it.
- `carcopilot_mockup_v09.html` is the visual target. Every field in the `Issue` schema (design doc §4) maps to something visible in that mockup.
- If something in the design doc seems wrong or contradictory, **flag it for the user** — do not silently deviate.

## What we're building right now

We are in **Phase 1** of the design doc §14: the Python core. Specifically:

- Project scaffold (pyproject.toml, Dockerfile, docker-compose.yml)
- `src/carcopilot/schema.py` — all dataclasses (use pydantic v2)
- `src/carcopilot/dtc_table.py` — seed from Appendix B
- `src/carcopilot/overrides.py` — live-data severity overrides
- `src/carcopilot/classifier.py` — the `classify()` function
- `src/carcopilot/obd_source.py` — `MockOBDSource` only (do not implement real BT yet)
- Fixtures in `tests/fixtures/obd_snapshots/` (misfire.json, overheat.json, healthy.json)
- Classifier tests in `tests/test_classifier.py`

**Do not start Phase 2 (Gemma adapter) until Phase 1 acceptance criteria pass.** Phase 1 is done when `pytest tests/test_classifier.py` passes for all three fixtures and the classifications match the polymorphic CTA decision table in design doc §11.1.

## Hard constraints — never violate

- **No cloud API calls.** Everything must work offline. The trust claim depends on this.
- **No location services.** Never ask for or use GPS. Artifacts that reference location use `"my current location"` as a placeholder string.
- **No mode 04** (clear DTCs). The agent does not expose this capability to the user.
- **Gemma never classifies.** The DTC lookup table is the source of truth for severity, route, cost, time. Gemma only generates narrative text on top.
- **Issue schema is the contract.** Adding or removing fields requires updating design doc §4 first.
- **Fail soft.** If Gemma errors, fall back to canned text. The app never crashes on the user.

## Conventions

- Python 3.11+
- Pydantic v2 for all schema. No stdlib dataclasses.
- `async`/`await` throughout the Gemma adapter and pipeline (per design doc §6, §7).
- Type hints on every public function.
- pytest for tests; pytest-asyncio for async tests.
- Tests in `tests/`, fixtures in `tests/fixtures/`.
- ruff for lint. No black; ruff handles formatting.

## Build commands

```bash
# Install deps
pip install -e ".[dev]"

# Run unit tests
pytest tests/

# Run only fast tests (skip integration)
pytest tests/ -m "not integration"

# Run integration tests (requires Ollama running)
pytest tests/ -m integration

# Bring up the dev environment
docker compose up -d

# Pull Gemma model (one-time)
docker compose exec ollama ollama pull gemma3:4b  # verify actual tag; see note below

# Run a demo end-to-end
docker compose exec app python demo/run_misfire.py
```

## Voice constraints (Phase 2 onwards, but relevant whenever you write user-facing strings)

Every user-facing string — whether generated by Gemma or hardcoded as fallback — must follow the voice rules in `prompts/system.md` (Appendix A of the design doc):

- One thought per sentence.
- Concrete, not abstract.
- When you name a problem, say what to do about it.
- No engineer vocabulary: never "polling," "telemetry," "diagnostic data," "execution," "edge," "agentic."
- Imagine the user is a friend on the phone, not a developer.

If you find yourself writing "executing diagnostic pipeline" or similar, stop and rewrite.

## When you finish a phase

1. Run the phase's acceptance criteria from design doc §14.
2. Commit with a message that names the phase: `feat(phase-1): schema + classifier + mock obd`
3. Pause and check in with the user before starting the next phase.

## Notes on Gemma model tag

The design doc references `gemma3:4b` as a placeholder. Before starting Phase 2, verify the current Gemma 4 tag on https://ollama.com/library — Gemma 4 may have a different tag name. Update `.env.example` and `docker-compose.yml` accordingly.

## What is explicitly out of scope (do not work on these without asking)

- Android app
- Real BT dongle integration (use MockOBDSource for the entire hackathon)
- Mode 02 freeze frame
- Mode 04 clear codes
- Location services
- Voice input/output
- Camera-based engine bay annotation
- Live local part pricing API integration
- Adaptive model tier selection
